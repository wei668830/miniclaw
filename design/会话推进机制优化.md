## 一、计划说明

### 1.1 背景

`main.CommandLineInteraction.stream()` 与 `Clerk._stream()` 实现了一套 **"判定式续跑"（裁判机制）**：当模型以纯文本收尾时，再次调用大模型作为"裁判"（`get_advance_messages` + 最近 5 条消息），裁判回复 `继续` 时追加 `{"role":"user","content":"继续"}` 并继续循环，否则结束。`main` 仅 agent 模式启用，`clerk` **无条件启用**。

### 1.2 现状问题（评审结论）

| 编号 | 问题 | 说明 |
| --- | --- | --- |
| P1 | 裁判字符串精确匹配脆弱 | `content.strip() == "继续"`，"继续。""继续执行""Continue"、带 reasoning 等一律误判为结束 |
| P2 | 无终止上限 | `while True` 无最大轮次/token/超时，裁判持续"继续"会无限循环、成本失控 |
| P3 | 每轮多一次 LLM 调用 | 延迟翻倍、成本增加，额外占用上下文预算 |
| P4 | 裁判视野过窄 | 只看最近 5 条，难以判断长任务整体进度 |
| P5 | "继续"污染历史 | 每次自推进写入 user/assistant 对，持续膨胀上下文，加速溢出 |
| P6 | clerk 无条件 + 无深度上限 | 子代理无限自推进，配合嵌套（layer）有递归失控风险；裁判调用漏传 `llm_usage_type` |
| P7 | 三处重复实现 | `main.stream`、`clerk._stream`、`actor` 复用同一函数，维护风险高 |
| P8 | 本质是给提示词问题打补丁 | 具备工具调用能力的模型，只要提示词写明自主性即可自推进，无需裁判 |
| P9 | 关联缺陷：`Actor._chat` 耦合错误 | `_chat` 使用 `get_advance_messages(self.messages)`，导致 **Memory 精简**与 **Planner 兜底问答**收到的是"决策者提示词 + 最近5条"而非各自 system 提示词，可能把"继续/结束"写进记忆/计划 |

### 1.3 决策

采用 **方案 B：提示词驱动的自主执行**——**移除裁判机制**，把"自主推进"的职责交给模型自身（通过 system 提示词约束）+ 常规工具循环，结束以"模型给出最终答复（无工具调用）"为准，可选哨兵标记用于状态识别。

### 1.4 目标

- 删除 `main`/`clerk` 中的裁判续跑逻辑与"继续"注入。
- 用提示词让 agent 模式与子代理"不向用户征求确认、持续推进、仅当完成或被阻塞时停止"。
- 修复 `Actor._chat` 与 `get_advance_messages` 的错误耦合。
- 保留必要的兜底护栏（工具循环最大次数、子代理最大层级），防止无限循环。
- 与 `记忆优化.md` 的上下文/记忆机制协同（不再因"继续"对膨胀上下文）。

## 二、方案 B 设计

### 2.1 自主执行提示词（核心）

- 新增可配置常量（`constant.py`）：
  - `AGENT_AUTONOMY_PROMPT`（env `CHAT_AGENT_AUTONOMY_PROMPT` 可覆盖），用于 **agent 模式主循环**，要点：
    - "你是自主代理，负责端到端推进任务，**无需**向用户征求确认或询问是否继续。"
    - "只要还能通过工具（读文件、写代码、执行命令、搜索等）取得进展，就**持续执行**，不要中途停下等待用户。"
    - "仅当：任务已完成、或确实被阻塞（缺少必要信息/权限/外部依赖，必须由用户提供）时才停止。"
    - "完成任务时，在答复末尾输出标记 `【TASK_DONE】`。"
  - `CLERK_AUTONOMY_PROMPT`（env `CHAT_CLERK_AUTONOMY_PROMPT` 可覆盖），用于**子代理**，要点同上（子代理只处理决策者下达的子任务）。
- 注入位置：
  - `main`：在 agent 模式下，将 `AGENT_AUTONOMY_PROMPT` 追加到 `CHAT_SYSTEM_PROMPT` 之后（`_compose_user_content` 合并进首条用户消息，沿用现有"system 保持简短"策略）；chat 模式不注入。
  - `clerk`：将 `CLERK_AUTONOMY_PROMPT` 追加到 `CLERK_SYSTEM_PROMPT` 之后（`merge_system_prompt_into_user`）。

### 2.2 移除裁判续跑逻辑

- `main.stream()`：删除 agent 分支中的
  - `chat_response_judgment = await self.client.chat(messages=get_advance_messages(self.messages), ...)`
  - `if chat_response_judgment.content.strip() == "继续": ... self.messages.append({"role":"user","content":"继续"}); continue`
  - 改为：正常文本收尾即 `return`（交还用户输入）。
- `clerk._stream()`：删除同样的裁判块，正常收尾即 `return None`。
- 同步移除不再使用的 `get_advance_messages` import（若确无其它引用）。

### 2.3 结束/完成识别（可选，轻量）

- 解析收尾文本是否含哨兵标记 `CHAT_TASK_DONE_TOKEN`（默认 `【TASK_DONE】`）：
  - agent 模式下若命中 → 打印 `[green]✅ 任务完成[/green]`，并在展示/入历史前剥离哨兵。
  - 未命中不影响流程（仅作为状态提示）。
- 不改变控制流：无论是否哨兵，纯文本收尾都结束本轮。

### 2.4 兜底护栏（防无限循环）

- **工具循环上限**：在 `stream()` / `_stream()` 的 `while True` 中对"连续工具调用轮次"计数，超过 `MINICLAW_MAX_TOOL_ITERATIONS`（默认 50）时停止并提示 `[yellow]⚠️ 工具调用达到上限，已暂停，请检查任务是否陷入循环[/yellow]`。
- **子代理层级上限**：`Clerk` 传入 `layer`，超过 `MINICLAW_MAX_SUBAGENT_LAYER`（默认 5）时拒绝新建子代理并返回提示。
- 上限仅作安全网，正常任务不应触达。

### 2.5 修复 `Actor._chat` 耦合（P9）

- `actor.py`：`Actor._chat` 中
  - 将 `messages=get_advance_messages(self.messages)` 改为 `messages=self.messages`。
- 影响面：Memory 精简、Planner 兜底问答将恢复正常（使用各自 system 提示词 + 自身消息）。
- 验证：详见 S4.x；需回归 `/memory`、`Planner.make` 兜底分支。
- `get_advance_messages` 与 `CHAT_ADVANCE_*` 环境变量随即**不再被使用**，保留函数与文档注释标记为 deprecated（不删除，避免破坏外部引用）。

### 2.6 与记忆优化方案的协同

- 移除"继续"注入后，agent 自推进不再产生额外 user/assistant 对 → 上下文增长显著变缓，降低记忆精简频率。
- 工具循环上限与 `记忆优化.md` 的 `_ensure_context()`（soft/hard 预算）协同：一个控"轮次"，一个控"token"。
- 工具结果裁剪（`shrink_tool_response`）仍按记忆方案执行，二者互不冲突。

## 八、风险与回滚

| 风险 | 影响 | 缓解 / 回滚 |
| --- | --- | --- |
| 模型不完全遵循自主指令，仍中途停下 | 自推进效果不如裁判 | 常见场景可接受（交还用户）；必要时用方案 A 精简版兜底 |
| 移除裁判后个别任务需用户二次"继续" | 交互略增 | 强化 `AGENT_AUTONOMY_PROMPT`；保留由子代理/计划驱动的推进 |
| `Actor._chat` 修复改变 Memory/Planner 行为 | 记忆/计划输出变化 | S4.3/S4.4 回归；如异常可按需回退（保留旧分支临时开关） |
| 工具循环上限过小误停 | 长任务被截断 | 默认 50 可配置上调 |
| 移除 import/代码误删 | 启动失败 | 每步 `py_compile`；必要时按 git 回滚 |

## 九、与记忆优化方案的执行关系

- 两份方案共用 `constant.py` / `.env.example` / `README.md`，建议**同批次修改以合并编辑**。
- 推荐实施顺序：先落地 `记忆优化.md` 的 Phase 1–4（context/history/memory），再执行本方案 Phase 1–4，最后统一做 Phase 5 端到端验收。
