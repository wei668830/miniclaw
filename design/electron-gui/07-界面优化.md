## 一、概述

本轮针对 MiniClaw 桌面应用（`python -m miniclaw ui` / `miniclaw.bat ui`）做了一批界面与启动体验优化，目标：

1. **启动不再"吓人"**：修复 `miniclaw.bat ui` 启动时刷屏的异常堆栈。
2. **更干净的外窗**：去掉系统应用菜单栏，并进一步改为**无框窗口**（自定义标题栏）。
3. **会话列表更简洁**：左侧不再展示会话 ID 与记录条数。
4. **对话更紧凑**：工具调用的展示大幅压缩，历史回放不再"一步一个气泡"。
5. **顺序更自然**：思考过程（reasoning）展示在工具调用之前。
6. **不再堆积空会话**：新建会话时若已存在空会话则直接复用。

改动横跨后端（启动入口、会话管理）与前端（Electron 主进程/预加载、渲染进程、样式）。

## 二、启动报错修复

### 现象

通过 `miniclaw.bat ui` 启动时，控制台打印一大段 Python traceback，结尾为：

```
urllib.error.URLError: <urlopen error timed out>
```

但后端与 Electron 实际都能正常启动（日志可见 `/api/health 200` 与 Electron 进程）。

### 根因

两处叠加：

1. `src/miniclaw/__main__.py` 的 `_wait_healthy()` 在后端尚未就绪时，用 `logger.opt(exception=True).debug(...)` 记录重试日志——这属于**预期内的暂时失败**，却把完整堆栈打印了出来。
2. `ui` 入口从未调用 `setup_logger()`，loguru 退回**默认 handler**（DEBUG 级、无格式、输出到 stderr），导致上述 DEBUG 级堆栈被直接刷到控制台。

### 修复

文件：`src/miniclaw/__main__.py`

- `_wait_healthy()`：改为只打印一行简报，不再输出堆栈。

  ```python
  except Exception as e:
      # 后端启动初期尚未监听端口属预期情况，仅打印一行简报，避免输出完整堆栈造成“报错”误导。
      logger.debug("后端尚未就绪，健康检查稍后重试：{}", e)
      time.sleep(0.3)
  ```

- `run_ui()`：入口处调用 `setup_logger()`，使 ui 进程日志遵循 `LOG_LEVEL` / `LOG_DIR` 等配置，与 `server` / `cli` 入口保持一致。

  ```python
  def run_ui(args):
      """启动桌面应用（后端 + Electron）。"""
      # 初始化日志系统：尊重 LOG_LEVEL/LOG_DIR 等配置，避免 loguru 默认 handler
      # 以 DEBUG 级、无格式方式输出（此前会把预期内的健康检查重试打印成完整堆栈）。
      setup_logger()
      ...
  ```

### 验证

重启后启动日志干净，`findstr Traceback/URLError` 结果为空，后端 `200`、Electron 正常。

## 五、对话区紧凑化

### 5.1 历史回放"一步一个气泡" → 按用户轮次合并（关键）

**现象**：工具调用展示占用空间过大。

**根因**：加载历史会话时，`mapHistory` 为**每条后端 assistant 消息**生成一个 UI 气泡，而模型每调用一次工具就是一条 assistant 消息。实测某会话 4 个用户轮次竟渲染出 **129 个助手气泡 / 126 张工具卡**，因此又高又散。

**修复**：文件 `frontend/src/store/appStore.ts`

`mapHistory` 改为按**用户轮次**合并连续的 `assistant` / `tool` 消息为一个 UI 消息（reasoning 合并到一处、工具卡归并到同一气泡、末尾正文保留），与**实时流式"一轮一个气泡"**的表现保持一致。

**效果**：同一会话从 **129 个助手气泡 → 4 个**（与 4 个用户轮次一一对应），143 张工具卡归并其中。

### 5.2 工具卡片进一步压缩

文件：`frontend/src/styles/index.css`

| 元素 | 调整前 | 调整后 |
| --- | --- | --- |
| `.tool-card` 外边距 / 圆角 / 字号 | `6px 0` / `8px` / `13px` | `2px 0` / `6px` / `12px` |
| `.tool-card-head` 内边距 / 行高 | `8px 10px` / 默认 | `2px 8px` / `1.4` |
| `.tool-toggle` 字号 | 默认 | `11px` |
| `.tool-card-body` 内边距 | `8px 10px` | `5px 8px` |
| `.tool-args` / `.tool-result` 最大高度 | `260px` | `180px` |

单张折叠卡片头部高度实测 **27px → 21px**。

### 5.3 思考过程展示在工具调用之前

**疑问**：为什么"先是工具、后是思考过程"？

**根因**：后端每个 assistant 步骤（含工具调用步骤）都会连同 `reasoning_content` 一起落盘；**实时流式**时思考随 `reasoning` 事件先于 `tool_call` 到达并渲染在工具卡片上方，本就"思考在上"。但旧版 `mapHistory` 遇到带 `tool_calls` 的消息时**只取 `tool_calls`、丢弃该消息的 `reasoning_content`**，于是回放旧会话时工具步骤的思考被丢掉，唯一能显示的思考来自最后一条文本消息——它渲染在工具卡片之后，就出现了"工具在前、思考在后"。

**修复**：`mapHistory` 按轮次合并后，`reasoning` 统一收纳在每个轮次气泡顶部，配合 `MessageItem` 既有渲染顺序（先 `reasoning` 后 `toolCards`），顺序恢复为：

```
思考过程 → 工具调用 → 正文
```

**验证**：加载真实历史会话，助手气泡子元素顺序为 `reasoning → tool(工具名)`。

## 六、空会话复用（不再堆积空会话）

**需求**：新建会话时，若已存在空会话，则复用而非再建一个空会话。

文件：`src/miniclaw/app/session_manager.py`

`SessionManager.create()` 逻辑调整：

- 新增 `_is_empty()`：除 `system` 外无任何消息即为空；
- `create()` 先查找已存在的空会话，存在则**复用**（可选切为当前），否则再新建。

```python
@staticmethod
def _is_empty(session: ChatSession) -> bool:
    """判断会话是否为空（除 system 外无任何消息）。"""
    return not any(m.get("role") != "system" for m in session.messages)

def create(self, activate: bool = True) -> ChatSession:
    for sid, existing in self._sessions.items():
        if self._is_empty(existing):
            if activate:
                self._current_id = sid
            logger.info(f"检测到已存在的空会话，直接复用: {sid}")
            return existing
    session = ChatSession()
    ...
```

放在**后端**实现，可同时覆盖 UI 与其它客户端（如 CLI）。

**验证**：连续 3 次 `POST /api/sessions` 均返回**同一个** `session_id`；会话列表中空会话始终只有 1 条。

## 八、回归与注意事项

- **生产模式必须重建**：Electron 生产加载 `frontend/dist`，改前端源码后需 `npm run build`；改主进程 `electron/main.js`、`preload.js` 需重启应用。
- **无框窗口**：窗口移动/关闭/最大化依赖 `TitleBar`，勿删。
- **实时流式 vs 历史回放**：两者现已统一为"一轮一个气泡、思考在上、工具随后、正文收尾"。
- 回归建议：`miniclaw.bat ui` 启动日志无 traceback；加载含工具调用的历史会话气泡数≈用户轮次数；连续点"新建会话"不增加空会话；窗口可拖拽/最小化/最大化/关闭。

## 九、第二轮：对话窗口交互优化（✅ 已实施，方案 A）

> 范围仅限桌面应用（UI）对话窗口。**需求二采用方案 A**（约定式 `choice` 选项块）；文件操作保留「复制路径」按钮；正文路径可点击（P2）本期未做；不做跨平台路径转换（直接显示后端返回的系统原生路径）。实施记录见 [9.9](#99-实施记录)。
### 9.1 需求

1. **生成文件的快捷操作**：对话中凡是产生了文件（写文件 / 编辑文件 / 生成计划等），都应能在消息里直接「打开文件」「打开所在文件夹」，无需手动去磁盘里找。
2. **交互确认可点击**：当模型需要用户确认或做选择时，其给出的选项应能**直接在界面上点击确认**，而不是让用户在输入框里手敲。

### 9.2 现状（代码定位）

| 相关点 | 现状 | 位置 |
| --- | --- | --- |
| 工具卡片 | 折叠卡片，仅「参数 / 结果」文本，无可点击操作 | `frontend/src/components/chat/ToolCallCard.tsx` |
| 文件类工具 | `write_file` / `edit_file` / `append_file`（入参 `file_path`；write/append 结果含绝对路径） | `src/miniclaw/agents/tools/file_io.py` |
| 计划工具 | `make_plans` 结果含「文件路径: <abs>」 | `src/miniclaw/cli/planner.py` |
| 打开文件底层能力 | 主进程已 `require('electron').shell`，但未暴露给渲染进程 | `frontend/electron/main.js` |
| 预加载桥 | 仅暴露连接信息与窗口控制 | `frontend/electron/preload.js` |
| 相对路径解析 | 后端 `_resolve_file_path` 基于 `os.getcwd()`（UI 后端 cwd = 项目根） | `src/miniclaw/agents/tools/file_io.py` |
| SSE 事件 | meta / reasoning / chunk / tool_call / tool_result / done / error（**无「等待用户输入」事件**） | `src/miniclaw/app/routers/chat_router.py`、`app/runtime.py` |
| 用户输入方式 | 仅输入框 | `frontend/src/components/chat/Composer.tsx` |

### 9.3 需求一：生成文件快捷操作

#### 9.3.1 交互形态

在工具卡片（及计划消息）上增加一条操作条：

```
📂 打开文件   ｜   🗂 打开所在文件夹   ｜   📋 复制路径
```

- 仅当卡片状态为 `done` 且能识别到文件路径时显示；
- 非 Electron 环境（浏览器调试）隐藏打开类按钮，降级为「复制路径」；
- 路径不存在时提示「文件不存在」。

#### 9.3.2 路径来源与解析

按优先级取候选路径：

1. **工具入参 `file_path`**：`write_file` / `edit_file` / `append_file`。前端已持有 `call.args`（JSON 字符串），可直接解析；
2. **工具结果文本中的路径**：`make_plans` 的「文件路径: …」，以及 write / append 结果里的「… to &lt;abs&gt;.」；
3. 兜底：识别不到则不显示操作条。

#### 9.3.3 相对路径 → 绝对路径（关键）

模型可能给出相对路径，而渲染进程（Electron）的工作目录与后端不一致，**前端无法自行解析**。因此由后端提供统一解析接口，复用既有逻辑 `_resolve_file_path`：

```
GET /api/system/resolve-path?path=<urlencoded>
→ { "input": "<原样>", "abs_path": "<绝对路径>", "exists": true/false, "is_dir": true/false }
```

实现位置：`src/miniclaw/app/routers/system_router.py`（只做解析与存在性判断，不读取文件内容）。

#### 9.3.4 打开动作（主进程 + 预加载）

**主进程**（`frontend/electron/main.js`）新增 IPC：

| 通道 | 作用 |
| --- | --- |
| `shell:open-path` | `shell.openPath(abs)`：用系统默认程序打开文件（或打开文件夹） |
| `shell:show-item-in-folder` | `shell.showItemInFolder(abs)`：打开所在文件夹并定位到该文件 |

**预加载**（`frontend/electron/preload.js`）在 `contextBridge` 暴露：`openPath(path)`、`showItemInFolder(path)`。

**类型声明**（`frontend/src/api/client.ts`）：在 `window.miniclaw` 上补两个方法签名。

#### 9.3.5 点击流程

1. 取得候选路径 → 2. `GET /api/system/resolve-path` → 3. 若 `exists=false` 提示「文件不存在」；否则调 IPC：
   - 「打开文件」→ `openPath(abs_path)`；
   - 「打开所在文件夹」→ 若为目录则 `openPath`，否则 `showItemInFolder(abs_path)`。

#### 9.3.6 组件改动

- **新增** `frontend/src/components/chat/FileActions.tsx`：接收 `path`，渲染三个按钮与加载/成功/失败态，供多处复用；
- `ToolCallCard.tsx`：解析出路径后，在卡片底部渲染 `<FileActions/>`；
- （可选 P2）消息正文中的绝对路径渲染为可点击的 chip。

### 9.4 需求二：交互确认选项可点击

提供两套方案，**本期建议 A**，B 作为进阶备选。

#### 9.4.1 方案 A（推荐本期）：约定式「选项块」+ 前端解析，零协议改动

**约定格式**：模型需要用户确认 / 选择时，在回复末尾输出一个语言标记为 `choice` 的代码块，每行一个选项：

```choice
继续执行
修改方案
取消
```

- 行文本既是**按钮文案**，也是点击后**发送的内容**；
- 支持 `标签 :: 发送内容`，以区分短标签与较长回复：

```choice
继续 :: 确认，请按当前方案继续执行
调整 :: 请先按我的意见调整，调整点是：
取消 :: 先不执行该步骤
```

**提示词注入（仅 UI）**：在 `src/miniclaw/app/runtime.py::_effective_system_prompt` 追加一段 UI 专用指令，要求「需要用户确认 / 选择时，用 `choice` 代码块列出选项」，**不影响 CLI**。

**前端渲染**：`MessageItem` 在 markdown 渲染前用正则提取并**剥离** `choice` 块，渲染为一行按钮（新增 `frontend/src/components/chat/ChoiceOptions.tsx`）；点击调用 `sendMessage(发送内容)`。

**状态处理**：
- `streaming` 期间按钮禁用；
- 已回答的选项高亮并禁用；
- 重新加载历史时，若后续存在与该选项等值的用户消息，则标记为「已选择」。

**优点**：不动后端 / SSE，历史回放天然可复现，改动小、风险低。
**局限**：依赖模型遵循约定（可选叠加「问句结尾 + 编号列表」的启发式解析兜底）；**不支持任务中途暂停**（模型须先结束本轮）。

#### 9.4.2 方案 B（进阶，后续可做）：后端 `ask_user` 工具 + SSE 事件 + 续流

- 新增特殊工具 `ask_user(question, options[])`（与 `make_plans` / `subtask_executor` 同机制：`invoke=None`，在 `_execute_tool_call` 特判执行）；
- 模型调用时：后端发 SSE `user_input_request {request_id, question, options[]}`，**结束本轮流**，会话记录 `pending_request`；
- 新增 `POST /api/chat/respond {session_id, request_id, value}`：写入用户选择并**续流**（延续同一助手气泡）；
- 前端渲染内联确认卡，点击后调 respond 接口继续。

**优点**：支持任务中途暂停确认、结构化、稳健。
**代价**：需改动 SSE 协议、会话状态与流式重入，工程量与风险较高。

> 建议：本期先做 **A** 覆盖「对话式确认」；若后续确需「工具执行到一半暂停等确认」，再上 **B**。

- **生产模式**：改前端源码需 `npm run build`；改 `main.js` / `preload.js` 需重启应用。

### 9.8 确认结论

1. **需求二采用方案 A**（约定式，低风险，本期实施）；方案 B 暂不实施。
2. **选项块语法**：采用「`choice` 代码块 + 每行一个选项」，并支持 `标签 :: 发送内容`。
3. **附加能力**：文件操作保留「复制路径」按钮；正文路径可点击（P2）本期不做。

## 十一、历史会话列表：轻量索引（方案 B）与删除会话

**目标**：左侧历史列表不再整读 JSONL（原实现按会话 `load_all()` 全量读取），改为**轻量索引**，并支持分页展示更多历史与删除会话。

### 11.1 方案 B：会话轻量索引

**索引文件**：`<MINICLAW_MEMORY_RAW_DIR>/index.json`（默认 `~/.miniclaw/memory/raw/index.json`）

```json
{ "s20261012-xxxx": { "created_at": "2026-10-12T16:14:37", "updated_at": "2026-10-12T16:15:02", "summary": "首条用户输入前 60 字" } }
```

- 字段仅 `created_at / updated_at / summary`（**不再统计 messages** —— 前端列表不展示）。
- summary 语义不变：JSONL 首行即第一条用户消息（系统提示词不落盘）；解析时按「【用户最新输入】」切分取用户正文并截断 60 字。

**写透（write-through）**：
- 新增 `src/miniclaw/cli/session_index.py`（`SessionIndex` 单例，`threading.Lock` + 原子写 `os.replace`）。
- `src/miniclaw/cli/history_store.py::append` 写盘后调用 `session_index.update_on_append(sid, msg)`：新会话建条目并置 summary，已有会话刷新 `updated_at`。

**列表读取**：`src/miniclaw/app/session_manager.py::list_sessions(limit, offset)`
- 只读索引（`session_index.all()`）+ 合并内存会话（空会话也出现）；
- 按 `updated_at` 倒序，`sessions[offset : offset+limit]` 分页；
- 索引过期（TTL 2s）时触发一次 `reconcile()` 对账。

**对账 reconcile**（`SessionIndex.reconcile`）：
- 扫描 `raw/s*.jsonl`；对**缺失条目**只读**首行**补齐（summary + 用文件 mtime 作时间）；对缺 summary 的条目补读首行；文件比索引新时回填 `updated_at`；清理文件已删除的条目。
- 用于覆盖 CLI 等**不经过本索引**的写入，以及历史遗留文件；**不整读任何文件**。

### 11.2 删除会话

- 后端 `SessionManager.delete(session_id)`：移除内存会话 → 删除 `raw/<sid>.jsonl` → 移除索引项 → 若为当前会话则清空 current。
- 接口 `DELETE /api/sessions/{session_id}`（新增），返回 `{session_id, deleted, current_session_id}`。
- 前端 `appStore.deleteSession(id)`：调用删除接口后 `refreshSessions()`；若删的是当前会话，则切到剩余首个会话，否则新建。

### 11.3 展示更多历史（分页）

- 接口 `GET /api/sessions?limit=50&offset=0`（新增 `offset`）。
- 前端 `appStore`：`sessionsLimit`（默认 50）；`loadMoreSessions()` 每次 +50 并刷新。
- 侧栏 `SessionSidebar`：`sessions.length >= sessionsLimit` 时显示「加载更多」。

### 11.4 前端交互（侧栏）

- 每项 hover（或选中）显示删除按钮 🗑，点击进入**内联二次确认**（✔ 确认 / ✕ 取消），确认后删除；流式进行时禁用。
- 底部「加载更多」按钮。
