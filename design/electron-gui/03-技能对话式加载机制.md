# 03 · 技能对话式加载机制（UI 端复刻）

> 关联文档：[02-后端API设计](./02-后端API设计.md) · [04-前端工程](./04-前端Electron工程设计.md)

> **本文是本次设计的核心约束**：技能必须「通过用户对话加载」，而非修改 system prompt；加载后不可卸载，只能新建会话重置。

---

## 一、机制本质

MiniClaw 的「技能」不是运行时插件，而是**一段注入到对话中的指引文本**：

- 技能 = 一个目录 `SKILL.md`（带 YAML frontmatter 的 `name` / `description`，正文为使用指引）。
- 加载技能 = 把该 `SKILL.md` 的**全文**拼接进**下一条用户消息**的文本里。
- 因此：技能随**对话上下文**生效，而非改 system prompt；模型通过「读到这条用户消息里的技能指引」来获得能力。

### 1.1 现有 CLI 实现（须对齐的基准）

参考 `src/miniclaw/cli/main.py`：

| 环节 | 方法 | 行为 |
|------|------|------|
| 扫描 | `_reload_skills()` | 扫描 `~/.miniclaw/skills/*/SKILL.md`，解析 frontmatter，得到 `(name, description, dir)` 列表 |
| 列出 | `_cmd_skill_list()` | 表格展示扫描结果 |
| 加载 | `_cmd_skill_load()` | 把未加载技能加入 `skills_preload = [(name, desc, dir), ...]` |
| **注入** | `_append_user_message()` | 把 `skills_preload` 中每个 `SKILL.md` 全文拼进用户消息：`**【技能名称：{name}，技能文件夹路径：{dir}，技能指引如下】：**\n\n{content}`，然后 `skills_preload.clear()` |
| 记账 | `_append_user_message()` | 加载记录追加到 `skills_loaded` |
| 重置 | `_init_messages()` | `self.skills_loaded.clear()`（仅初始化/新建会话时） |

> **系统提示词处理（更新）**：完整系统提示词**不写入历史（jsonl）**，改为在**每次构造请求时**由 `_build_request_messages()` 注入到「第一条用户消息」（在副本上、确定性、不落盘）；system 消息仍只保留简短指令。技能注入则仍随对话落盘（属该轮对话上下文）。

### 1.2 SKILL.md 格式

```markdown
---
name: web-search
description: 联网搜索（豆包搜索）。当需要获取实时信息时加载本技能。
---

# 联网搜索技能

## 何时使用
……

## 如何使用
调用 `web_search` 工具，参数……

## 注意事项
……
```

## 二、生命周期（状态机）

```
┌─────────┐  扫描   ┌──────────┐  /skill-load   ┌──────────────┐
│ SKILL.md │──────►│ 可用技能  │──────────────►│ skills_preload│
└─────────┘        │ (scanned)│   (排队)        └──────┬───────┘
                    └──────────┘                       │
                                                       │ 下一条用户消息
                                                       ▼
                          ┌───────────────┐   注入 SKILL.md 全文
                          │ skills_loaded │◄──── 到该用户消息文本
                          │ (只增不减)     │
                          └───────┬───────┘
                                  │
                          唯一重置入口：新建会话
                                  ▼
                            （清空 = 新会话）
```

**三条铁律：**

1. **加载动作只「排队」**：真正生效在**下一条用户消息**（因而是"对话式"的）。
2. **不可卸载**：本会话内 `skills_loaded` 只增不减，无卸载/禁用接口。
3. **仅新建会话可重置**：`POST /api/sessions` 创建全新会话，`skills_loaded` 为空。

### 4.2 注入点复用

`ChatSession.append_user_message()` 复刻 `_append_user_message` 逻辑：

```python
def append_user_message(self, user_input: str) -> None:
    if self.skills_preload:
        text = user_input.strip()
        for (name, desc, skill_dir) in self.skills_preload:
            md = skill_dir / "SKILL.md"
            if not md.exists():
                continue
            content = md.read_text(encoding="utf-8")
            text += f"\n\n**【技能名称：{name}，技能文件夹路径：{skill_dir}，技能指引如下】：**\n\n{content}\n\n"
        self.skills_loaded.extend(self.skills_preload)   # 记账
        self.skills_preload.clear()                       # 只注入一次
        self._append_message({"role": "user", "content": self._compose_user_content(text)})
    else:
        self._append_message({"role": "user", "content": self._compose_user_content(user_input)})
```

> **复用优先**：若完成 `CommandLineInteraction → ChatSession` 抽取，则 CLI 与 API 共享**同一份**注入代码，彻底避免语义漂移。

## 五、UI 端交互设计

技能加载提供**两种等价入口**，二者最终都触发 `POST /api/skills/load`：

### 入口 A：对话内斜杠命令（与 CLI 体验一致）

- 用户在输入框输入 `/skill-load web-search`（或 `/skill-load a,b`）。
- 前端拦截以 `/` 开头的输入，识别为**命令**而非普通消息：
  - `skill-list` / `skill-load` → 调技能 API；
  - 其余命令（`session-*`、`llm`、`agent`、`web-search` 等）→ 调对应 API；
  - 结果以「系统消息气泡」渲染到对话流（不进入 LLM 上下文）。
- 与 CLI 的 `commands.py` 语义一一对应。

### 入口 B：技能面板

- 侧边栏「技能」页：
  - 顶部：**当前会话已加载技能**（带「本会话内不可卸载」徽标，只读）。
  - 列表：全部可用技能，每项含「名称 / 描述 / 加载按钮」；已加载项按钮置灰显示「已加载」。
- 点击「加载」→ 调 `POST /api/skills/load` → Toast 提示「已加载，将在下一条消息生效」。

### UI 状态提示（必须）

| 场景 | 提示文案（示例） |
|------|------------------|
| 加载成功 | 「技能 `web-search` 已加载，将在你**下一条消息**中生效」 |
| 重复加载 | 「该技能本会话已加载，无需重复」 |
| 尝试卸载 | 不提供卸载入口；如用户询问，提示「技能本会话不可卸载，如需重置请**新建会话**」 |
| 新建会话后 | 已加载技能清空；面板显示「本会话尚未加载技能」 |

### 消息渲染约定

- 技能注入是**后端内部行为**，前端**不应**把注入后的超长用户消息原样回显给用户（避免刷屏）。
- 前端只回显用户**原始输入**；若需透明化，可在消息旁挂一个「已注入技能：web-search」的小标签（由后端在 `meta` 事件回传 `injected_skills`）。

> 建议：`/api/chat/stream` 的 `meta` 事件增加字段 `injected_skills: ["web-search"]`，供前端做透明化标签。

## 六、为什么不用「改 system prompt」方式

| 维度 | 对话式注入（本方案） | 改 system prompt |
|------|----------------------|------------------|
| 兼容现有机制 | ✅ 完全一致 | ❌ 需改核心提示词装配 |
| 网关长度限制 | ✅ 走用户消息，规避 system 长度限制 | ❌ 部分网关对长 system 直接断连 |
| 技能生效范围 | ✅ 天然会话级、可追溯（在上下文中） | ❌ 改后对所有会话生效，难隔离 |
| 「加载后不可移除」语义 | ✅ 自然满足（历史消息不可变） | ⚠️ 需额外状态管理 |

> 结论：沿用对话式注入，既是**约束**，也是**更符合现有架构**的选择。

---

## 七、边界与注意事项

1. **注入一次**：`skills_preload` 在注入后立即清空，避免每条消息重复膨胀。
2. **已加载去重**：`POST /api/skills/load` 对 `skills_loaded` 中已有技能去重（返回 `already_loaded`）。
3. **技能路径安全**：只扫描 `MINICLAW_SKILLS_DIR`（默认 `~/.miniclaw/skills`）下一级目录，防止路径穿越。
4. **正文大小**：单技能 `SKILL.md` 过大时提示（可复用 `DEFAULT_TOOL_OUTPUT_MAX_TOKENS` 类似阈值），避免一次性撑爆上下文。
5. **与上下文预算协同**：技能注入后若触发软/硬阈值，`ensure_context()` 会按既有策略精简（技能正文属用户消息，通常保留）。
6. **持久化**：`skills_loaded` 属于会话运行态；会话导出（Markdown）应包含「已加载技能」清单以便复现。

## 八、验收点

- [ ] UI 通过斜杠命令 `/skill-load` 与技能面板**两种方式**均可加载技能。
- [ ] 加载后，**下一条**用户消息确实携带 `SKILL.md` 全文（后端日志/调试可见）。
- [ ] 已加载技能在本会话**无法卸载**；重复加载被去重。
- [ ] **新建会话**后 `skills_loaded` 清空（技能可重新加载）。
- [ ] CLI 的 `/skill-list`、`/skill-load` 行为**不受影响**（回归通过）。
- [ ] 前端不回显被注入的超长文本，仅以标签透明化。
