# 01 · 总体架构设计

> 关联文档：[README](./README.md) · [02-后端API设计](./02-后端API设计.md) · [04-前端Electron工程设计](./04-前端Electron工程设计.md) · [05-启动流程](./05-启动流程与__main__集成.md)

## 一、目标

为 MiniClaw 提供桌面 GUI，使非 CLI 用户也能完成以下核心操作：

1. **对话**：与 Agent 流式对话，展示思考过程、工具调用、任务完成标记（`【TASK_DONE】`）。
2. **会话**：新建 / 列出 / 加载 / 恢复 / 导出会话。
3. **技能**：查看技能列表，并通过**对话方式加载**技能。
4. **配置**：切换大模型、调整采样参数、切换运行模式（agent/chat）、开关联网搜索。

一句话：**把现有 CLI 能力可视化，且技能加载语义与 CLI 完全一致。**

---

## 二、设计原则

| 原则 | 说明 |
|------|------|
| **复用优先** | 不重写 Agent 核心。后端通过薄封装复用 `agents/`、`cli/stream_runner.py`、`utils/` 等既有能力。 |
| **单一事实来源** | 技能扫描、命令语义等尽量与 CLI 共用同一份实现，避免两套逻辑漂移。 |
| **技能语义一致** | UI 端技能加载 = CLI 端 `/skill-load`，均通过「用户消息注入 SKILL.md 全文」实现，加载后不可卸载。 |
| **本地闭环** | 后端仅监听 `127.0.0.1`，随机端口 + 一次性 Token 鉴权；不外联、不暴露公网。 |
| **单向依赖** | 前端只依赖后端 HTTP/SSE 契约；后端不感知前端实现。契约变更需同步文档。 |
| **源码运行优先** | 一期以「源码 + 依赖环境」方式运行（`miniclaw ui`），**不做打包分发**；面向非技术用户分发列为可选后续。 |

## 五、进程模型

桌面上共 3 类进程：

| 进程 | 承载 | 生命周期 | 说明 |
|------|------|----------|------|
| **Electron 主进程** | Node.js | 应用级 | 创建窗口、托管后端子进程、下发连接信息 |
| **Electron 渲染进程** | Chromium | 窗口级 | 运行 React UI，直连后端 HTTP/SSE |
| **Python 后端** | uvicorn | 应用级 | FastAPI 服务；由主进程或 `__main__` 拉起 |

**两种启动来源（见文档 05）：**

- 方式 A（推荐，面向最终用户）：`miniclaw ui` → `__main__` 启动后端 → 再启动 Electron 主进程 → 主进程复用已有后端。
- 方式 B（面向开发/独立分发）：直接启动 Electron → 主进程自行 `spawn` Python 后端。

> 无论哪种方式，**后端进程句柄由「先启动方」持有**，退出时由其优雅关闭（`SIGTERM` / `terminate`），前端**禁止**通过 shell 命令杀 Python 进程。

### 5.1 单实例约束（只允许启动一个实例）

| 层级 | 手段 | 说明 |
|------|------|------|
| Electron 应用级 | `app.requestSingleInstanceLock()` | 拿不到锁直接 `app.quit()`；`second-instance` 事件中聚焦已有窗口 |
| 运行态锁文件 | `~/.miniclaw/state/miniclaw-ui.lock` | 记录 `{pid, port, token, started_at}`；启动时若 PID 存活则判定已有实例 |
| 后端端口级 | 固定默认端口 7909 | 若 7909 已被占用，启动前判定是「本应用后端」还是「他人占用」 |
| 后端自保护 | 启动时写锁 + 父进程看门狗 | 防止孤儿实例；见 5.2 |

**启动判定逻辑：**

1. 尝试获取 Electron 单实例锁；失败 → 聚焦已有窗口并退出。
2. 检查 `miniclaw-ui.lock`：存在且 PID 存活 → 已有实例 → 聚焦/退出；PID 已死 → 视为**陈旧锁**，清理后继续。
3. 检查默认端口 7909：
   - 未被占用 → 正常启动。
   - 被占用且健康探针 `/api/health` 返回本应用特征（或锁文件指向它）→ 判定为**孤儿后端**，按策略**先终止再启动**。
   - 被占用但非本应用 → 回退到空闲端口启动。

### 5.2 生命周期强绑定：UI 关闭 ⇒ 后端同步销毁

**核心原则：后端进程的存亡与窗口的存亡绑定。**

| 触发点 | 处理 |
|--------|------|
| 用户关闭窗口（`window-all-closed`） | 触发应用退出流程 → 终止后端 |
| 应用退出（`before-quit` / `will-quit`） | 终止后端子进程（`SIGTERM`，超时 `SIGKILL`）；删除锁文件 |
| 渲染进程崩溃 | 主进程检测到后按策略重启窗口或整体退出（退出时必须带走后端） |
| UI 被强杀（`SIGKILL`，错过钩子） | 由**后端看门狗**兜底：父进程/连接消失时后端自我退出 |
| `miniclaw ui` 形态 A | `electron_proc.wait()` 返回后，`backend_proc.terminate()`；最终 `finally` 再兜底 |

**后端看门狗（防孤儿）—— 双保险：**

1. **父进程监视**：后端启动时通过 `MINICLAW_PARENT_PID` 拿到父 PID，后台线程定时检查父进程是否存在，不存在则 `os._exit(0)`。
2. **stdin EOF 监视**：父进程以管道方式 spawn 后端；当父进程退出，管道关闭，后端读 stdin 得到 EOF → 自我退出。

> 这两个机制保证：即使 Electron 未走正常退出钩子（崩溃/被 kill），后端也会在秒级内自动销毁，**不会残留**。

## 六、通信与安全

| 项 | 设计 |
|----|------|
| 监听地址 | `127.0.0.1`（仅本机） |
| 端口 | 默认 **7909**（`--port` / `MINICLAW_UI_PORT` 可覆盖，独立于 `server` 的 `SERVER_PORT`）；若 7909 被占用则回退到空闲端口，启动后回传前端 |
| 鉴权 | 启动时生成一次性随机 `token`，前端所有请求带 `Authorization: Bearer <token>`；后端启动即校验，退出即失效 |
| CORS | 生产环境收敛为仅允许 Electron 来源；开发环境放开 `localhost` |
| 传输 | 普通请求用 JSON；聊天流用 **SSE**（`text/event-stream`） |
| 大文本 | 前端不落盘敏感信息；API Key 仅在后端与 `.env`，前端仅显示掩码（`masking_str`） |

## 八、端到端数据流（以「发一条消息」为例）

```
渲染进程                主进程                后端(FastAPI)              工作目录
   │  用户输入+发送        │                       │                        │
   ├──POST /api/chat/stream(session_id, message)──►│                        │
   │                       │                       │ 1. 取会话运行时         │
   │                       │                       │ 2. skills_preload 注入 │
   │                       │                       │    到本条用户消息       │
   │                       │                       │    (SKILL.md 全文)      │
   │                       │                       │ 3. 拼接历史→messages    │
   │                       │                       │ 4. 调 LLM 流式          │
   │◄──SSE: chunk--------──┼───────────────────────┤                        │
   │◄──SSE: tool_call-----─┤                       │ 执行工具               │
   │◄──SSE: chunk---------─┤                       │                        │
   │◄──SSE: done----------─┤ 5. 持久化消息 ◄───────┼───────────────────────►│ chat_context
   │  渲染 & 滚动           │                       │                        │
```

**技能注入的关键**：第 2 步中，`skills_preload` 中的每个技能把 `SKILL.md` 全文追加进**本条用户消息**文本后清空；加载记录写入 `skills_loaded`（会话内只增不减）。

## 九、关键技术决策与取舍

| 决策点 | 选择 | 理由 / 备选 |
|--------|------|-------------|
| 前端框架 | **Electron + React + Vite + TypeScript** | 团队 Web 生态成熟、组件丰富；备选 Vue、Tauri。 |
| 前后端通信 | **HTTP + SSE**（渲染进程直连后端） | 语义简单、与现有 `StreamingResponse` 天然契合；备选 WebSocket（双向但复杂）。 |
| 后端托管 | **主进程 / `__main__` 统一托管** | 避免用户手动起服务；保证生命周期一致。 |
| 会话运行时 | **后端内存态 + 工作目录持久化** | 与 CLI 的 `skills_loaded`/`history_store` 语义一致。 |
| 技能注入 | **用户消息文本拼接**（不改 system） | 唯一符合现有机制的做法；规避网关对 system 长度限制。 |
| 打包 | **一期不打包**（源码依赖环境运行） | 单机自用无需分发；仅当需面向非技术用户分发时，再引入 electron-builder + PyInstaller（并可评估 Tauri 减体积）。 |

## 十、与 CLI 的关系

- CLI（`miniclaw cli` / 默认）**继续可用**，本次改造保证其行为不变。
- 共享层抽取原则：**能复用的抽到 `utils/` 或独立运行时**，CLI 与 API 都调用它；避免为 UI 复制一份逻辑。
- 命令语义映射见 [02-后端API设计.md](./02-后端API设计.md) 的「CLI↔API 对照表」。
